## 三、手写让我理解了什么

这部分是真正的收获，**每条都对应一次实测**。

### 1. 循环的本质很简单

就是一个 `for step in range(MAX_STEPS)`，终止条件是「模型不再请求工具」。

框架把它包装成 `AgentExecutor`，但去掉包装之后就是这十几行。**理解了这一点，再看任何 Agent 框架都会觉得眼熟。**

### 2. 文本解析比想象中脆弱

ReAct 靠 prompt 约定格式，模型随时可能漂移。

实测中模型表现良好（格式稳定、没有编造 Observation），但**我在探测阶段写错过解析顺序**——先检查 `Action` 再检查 `Final Answer`，结果把「模型正确地直接回答」误判成「格式错误」，会导致死循环重试。

**教训：解析顺序必须是 `Final Answer` 优先。**

### 3. 模型会编造 Observation

即使 prompt 里明确写了「不要自己编造 Observation」，也不能依赖它自觉。

**必须在代码层强制截断**模型输出里 `Observation:` 之后的内容——因为如果模型自己编的执行结果进了历史，它会基于虚假事实继续推理，而错误看起来完全合理。

### 4. 上下文成本是累积的

每一步的输入 = 之前所有步骤的累积。

实测：读取一个 3203 字符的日志文件，**不做任何压缩时总输入 2175 tokens**；而且这个增长取决于 Observation 有多长——如果读的是 10 倍大的文件，成本就涨 10 倍。

### 5. 压缩策略必须匹配内容的「信息分布」

同一个任务（分析 `data/app.log`），四种策略的实测结果：

| 版本 | 策略 | 总输入 | 信息覆盖 | 成本 |
|---|---|---|---|---|
| v0 | 不压缩 | 2175 | 5/5 | ¥0.00438 |
| v1 | 头尾截断 800 字符 | 1032 | **3/5** | ¥0.00283 |
| v2 | 按日志级别筛选 · 40 行 | 1866 | 5/5 | ¥0.00390 |
| **v3** | **按日志级别筛选 · 20 行** | **1253** | **5/5** | **¥0.00317** |

**三个关键结论：**

- v1 输入 token 降 53%、总成本降 35%，但**丢失了「慢查询」和「认证失败」**——因为这两类问题分散在日志中间，而头尾截断只保留两端
- v2 策略对了但参数太松：52 行的文件里 35 行含 ERROR/WARN，`max_lines=40` 等于几乎全留，只省 11%
- **v3 是唯一「信息无损 + 显著省钱 + 最快」的组合**，而且答案质量比不压缩更高（多了日志级别标注和因果链分析）

> **删对东西，比删得多更重要。** 去掉 68% 的噪声行之后，模型的注意力集中在高密度信息上，分类和关联分析反而做得更好。

**不同内容类型要用不同策略：**

| 内容类型 | 信息分布 | 合适策略 |
|---|---|---|
| 文章 / 代码 | 两端集中（开头是背景、结尾是结论） | 保留头尾 |
| 日志 | 按级别分散（ERROR/WARN 散落全篇） | 按关键词筛选 |

### 6. 工具说明的表示方式很贵

| 表示方式 | 大小 | 用在哪 |
|---|---|---|
| 完整 JSON Schema | 1272 字符 | function calling 的 `tools` 参数 |
| 自然语言列表 | 279 字符 | ReAct 的 prompt |
| **倍率** | **4.56x** | |

而且**这个差额每一步都要重发一次**。

测过精简方案（去掉 `title`、`additionalProperties` 等对模型无用的字段）：只省 13%。**说明 token 大头是 description 的正文，不是结构字段**——想真正降低输入成本，只能精简工具描述的文字，但那会降低模型的选择准确率，是另一个权衡。

## 四、两种范式的实测对比

环境：deepseek-flash，均关闭思考模式（`reasoning_effort: "none"`），上下文压缩策略一致。

| 问题 | 实现 | 步数 | 输入 token | 输出 token | 耗时 | 成本 |
|---|---|---|---|---|---|---|
| 幂运算 | function calling | 2 | 1440 | 56 | 1.48s | ¥0.001797 |
| 幂运算 | ReAct | 2 | 634 | 70 | 1.39s | ¥0.000987 |
| 日志总结 | function calling | 2 | 2064 | 436 | 2.66s | ¥0.004113 |
| 日志总结 | ReAct | 2 | 1254 | 375 | 2.86s | ¥0.002974 |
| 双工具 | function calling | 2 | 1487 | 98 | 1.45s | ¥0.002029 |
| 双工具 | ReAct | 3 | 1068 | 132 | 2.64s | ¥0.001724 |

### 差异及其归因

| 差异 | 数据 | 归因 |
|---|---|---|
| ReAct 输入 token 全面更低 | −28% ~ −56% | JSON Schema 比自然语言说明长 4.56 倍，且每步重发 |
| ReAct 偶尔需要更多步数 | 双工具任务 3 步 vs 2 步 | **ReAct 的文本格式一次只能输出一组 Action，不支持并行工具调用** |
| ReAct 延迟更高（复杂任务） | 2.64s vs 1.45s（+82%） | 多一次往返，而每次往返都要重发全部上下文 |
| ReAct 有格式解析失败风险 | — | 结构化协议由 API 保证；文本格式靠模型自觉遵守 prompt |
| ReAct 能看到推理过程 | — | `Thought` 是可见的；function calling 只能看到它要调什么工具 |

**最重要的发现**：两种范式的差别不只是「输出格式」，还有**并行能力**。function calling 在一次响应里可以返回多个 `tool_calls`，而 ReAct 的文本格式没有数组结构来表达这个。

## 五、什么时候用框架

- **生产系统、多人协作**：需要统一的抽象让别人快速读懂
- **复杂编排**：分支、循环、人工介入、中断后恢复（这是 LangGraph 的核心价值）
- **大量生态集成**：几十个工具、多种向量库、多个模型供应商
- **需要现成可观测性**：不想自己维护 trace 系统

## 六、什么时候手写

- **逻辑简单**：一个循环 + 几个工具就够了
- **需要精细控制**：成本、延迟、提示词、上下文策略都要自己调
- **调试和理解原理**：框架出黑盒问题时，手写过的人能定位
- **依赖少**：框架的大版本升级常有破坏性变更，手写没这个负担

---

## 七、一句话总结

> 框架解决的是**集成和规模化**问题；
> 手写解决的是**理解和可控性**问题。
>
> **先手写一遍，再用框架——这样你才能判断框架的行为对不对。这是最重要的收益。**
