## 一、异步解决什么问题

**把「等待时间」重叠起来。**

计算机只做两类事：

| 类型 | 例子 | 占 CPU 吗 |
|---|---|---|
| 计算 | 算数、解析 JSON | ✅ 占 |
| **等待** | 等网络、等磁盘、等定时器 | ❌ **不占** |

同步代码把「等待」也当成「占用」——线程被阻塞住，什么也干不了。

### 用本项目量化

一个典型的 Agent 任务耗时约 1.38 秒，拆开看：

| 阶段 | 耗时 | 占本机 CPU 吗 |
|---|---|---|
| 构造请求 | < 1ms | ✅ |
| 网络传输 | ~200ms | ❌ |
| 服务端生成回答 | ~1000ms | ❌（服务端的 CPU） |
| 解析响应 + 执行工具 | < 2ms | ✅ |

**本机 CPU 只工作了约 3 毫秒，剩下 1377 毫秒全在等——等待占比 99.8%。**

这就是并发几乎「免费」的原因：不是在挤 CPU，而是把本来要浪费的等待利用起来。

## 二、异步 vs 多线程

**核心区别：谁决定「何时切换任务」。**

| | 多线程 | asyncio |
|---|---|---|
| 调度方式 | **抢占式**（操作系统随时打断） | **协作式**（只有 `await` 时让出） |
| 切换开销 | 陷入内核，保存寄存器与栈 | 用户态函数返回，快 1~2 个数量级 |
| 单个实例内存 | 约 **1 MB** | 约 **几 KB** |
| 能开多少 | 几百到几千 | **几万到几十万** |
| 共享变量 | **必须加锁** | **不需要**（单线程执行） |
| **一个任务卡住** | 只影响自己 | **拖死所有人** ⚠️ |
| 典型 bug | 竞态条件、死锁 | 忘记 await、阻塞调用卡死循环 |

### 最关键的差异

| | 一个任务卡住的后果 |
|---|---|
| 多线程 | 线程 A 卡住，B、C 照常跑（隔离性好） |
| 异步 | 协程 A 没让出 → **事件循环卡死，B、C 全部停摆** |

**这解释了为什么异步代码对「阻塞调用」零容忍。**

实测（第 1 段实验 2）：3 个各 1 秒的同步阻塞任务，用 `gather` 跑，耗时 **3.00s**——并发完全失效，且不报任何错。

### 单线程的隐藏收益：不用加锁

任何时刻只有一个协程在执行，所以：

```python
# 多线程：必须加锁
with lock:
    counter += 1

# 协程：直接写，安全
counter += 1
```

**省掉锁，就省掉了一整类 bug。**

## 三、什么时候不该用异步

**CPU 密集时不该用。**

事件循环只有一个线程，一段不让出的计算会把它占死，连带着所有等待中的 IO 任务一起停摆。

### 判断标准

> **看「等待时间 ÷ 总时间」的比例：**
> - 等待占比 **> 80%** → IO 密集，适合异步 ✅
> - 等待占比 **< 20%** → CPU 密集，不适合 ❌

| 任务 | 等待占比 | 适合异步吗 |
|---|---|---|
| 调用 LLM | 99.8% | ✅ |
| 读文件 | ~90% | ✅ |
| 单次 `eval("3**15")` | ~0%（微秒级） | ⚠️ 但不值得管 |
| **1000 个本地 embedding** | ~0%（50 秒纯计算） | ❌ **绝对不行** |

### 本项目将来会遇到哪些 CPU 密集场景

做 RAG 项目时（Day 14 之后）：

| 场景 | 为什么是 CPU 密集 |
|---|---|
| 本地 embedding 模型 | 纯矩阵计算 |
| 本地 rerank（cross-encoder） | 每个候选都要跑一遍模型 |
| 大文件解析（100MB PDF/Excel） | 解析与分块 |
| 本地小模型推理 | 没有 GPU 时全是 CPU |

### 三种场景的完整决策

| 你要做的事 | 用什么 |
|---|---|
| **有异步库** | 直接 `await`（`httpx.AsyncClient`） |
| **同步 IO 库** | `asyncio.to_thread` |
| **同步 CPU 密集** | **`run_in_executor(ProcessPoolExecutor)`** |

## 四、`asyncio.to_thread` 的定位

**它是「兼容层」，不是「优化手段」。**

解决的是**生态兼容**问题——标准库的文件 IO 和大量第三方库都是同步的，没有异步版本，不可能为了用 asyncio 就全重写。

### 本项目里的应用

```python
async def adispatch(name: str, raw_args: str) -> str:
    ...
    if inspect.iscoroutinefunction(fn):
        return await fn(**validated)  # 异步工具
    return await asyncio.to_thread(fn, **validated)  # 同步工具（read_file 等）
```

### 三个硬限制

| 限制 | 数值 | 影响 |
|---|---|---|
| 线程池上限 | `min(32, CPU核数 + 4)` | 超过就排队 |
| 每线程内存 | 约 1 MB | 1000 个线程 = 1 GB |
| **GIL** | 同一时刻只有一个线程执行字节码 | **对 CPU 密集完全无效** |

### 关键区分

| 场景 | `to_thread` 有效吗 |
|---|---|
| 同步 **IO** 函数 | ✅ 有效 |
| 同步 **CPU** 函数 | ❌ **无效**（GIL 串行化） |

**大规模并发 IO 的终点是原生异步库**——这就是 `httpx` 要专门维护 `AsyncClient` 的原因。

## 五、并发 vs 并行

**并发是「同时处理」，并行是「同时执行」。**

| 维度 | 并发 | 并行 |
|---|---|---|
| 定义 | 同时**处理**多个任务 | 同时**执行**多个任务 |
| 需要多核吗 | ❌ 不需要 | ✅ 必须 |
| 关注点 | **结构**——怎么组织任务 | **执行**——用多少硬件 |
| Python 实现 | asyncio、多线程 | **多进程** |
| 提升什么 | 吞吐（等待重叠） | 算力（真多核） |

**本项目的 asyncio 是并发，不是并行**——单线程，同一时刻只有一段代码在执行。

8.3s → 3.2s 的收益来自「等待重叠」，不是「算力增加」。**在单核机器上效果一样。**

### Python 特有的坑

因为 GIL，**多线程做 CPU 计算也是串行的**——「多线程」在 Python 里提供的往往是并发，不是并行。

| 想要 | Python 里用什么 |
|---|---|
| 并发（IO 重叠） | asyncio 或 多线程 |
| **并行（CPU 多核）** | **多进程** |

## 六、并发能省成本吗

**不能。它只省时间。**

### 实测证据

| 并发上限 | 串行 token | 并发 token | 差异 |
|---|---|---|---|
| 3 | 10087 | 10028 | **−0.6%** |
| 5 | 10100 | 10095 | **−0.05%** |

**两次都在 1% 以内**（差异来自服务端计数波动，不是并发引起的）。

> **异步优化的是「时间」，不是「工作量」。**
> 想要省成本是另一个方向的事（减少 token、利用缓存、换便宜模型），和异步无关。

## 七、实测数据汇总

环境：`deepseek-flash`，关闭思考模式（`reasoning_effort: "none"`）

### 表 1：异步 LLM 调用

| 任务数 | 串行 | 并发 | 加速 |
|---|---|---|---|
| 1 | 0.95s | 0.49s | — ※ |
| 3 | 2.25s | 1.16s | 1.9x |
| 6 | 4.49s | 1.68s | 2.7x |

> ※ 单任务是噪声（首次调用含 DNS 冷启动），参考价值低。

### 表 2：客户端复用

| 运行 | 独立 client | 共享 client | 提升 |
|---|---|---|---|
| 第一次 | 1.84s | 0.88s | **约 +52%** |
| 第二次 | 1.78s | 0.70s | **约 +61%** |

**归因（本地实测）**：`httpx.AsyncClient()` 初始化会同步加载 CA 证书。
连续 20 次构造实测中位数 **149.6ms**（均值 154.2ms），每次约 **150ms**；
6 次合计约 **900ms**——与实测的运行时间差异（0.96s / 1.08s）吻合。

### 表 3：工具并发（零 API 成本）

| 工具类型 | 串行 | 并发 | 加速 |
|---|---|---|---|
| 异步工具（1.5s × 3） | 4.52s | **1.50s** | **3.0x** |
| 同步工具 + `to_thread`（1.0s × 3） | 3.00s | **1.00s** | **3.0x** |
| 同步工具，**漏掉** `to_thread` | 3.00s | **3.00s** | **1.0x** ❌ |

### 表 4：批量并发（端到端）

| 并发上限 | 串行 | 并发 | 实测加速 | 理论上限 |
|---|---|---|---|---|
| 3 | 7.87s | 3.52s | **2.2x** | 2.5x |
| 5 | 8.25s | **2.02s** | **4.1x** | 5.0x |

**理论加速的算法**：

```
limit=3，5 个任务 → ⌈5/3⌉ = 2 批 → 5/2 = 2.5x
limit=5，5 个任务 → 1 批 → Σ任务耗时 ÷ max任务耗时
```

**结论：加速比的上限由「批次」和「最慢的那个任务」共同决定，不是简单的「任务数」。**

### 表 5：失败隔离与重试

故障注入：把一个任务的 `llm_model` 改成不存在的名字 → 服务端返回 **400**

| 场景 | 串行 | 并发 | 成功数 | 结果 |
|---|---|---|---|---|
| **无隔离**（初版） | — | — | 0/6 | ❌ **程序崩溃** |
| 有隔离，无重试 | 7.91s | 3.21s | **5/6** | ✅ 可追溯 |
| 有隔离 + 重试 | **9.09s** | **3.22s** | **5/6** | ✅ 放弃并记录 |

## 八、踩过的坑

### 坑 1：同步阻塞静默毁掉并发

```python
async def bad_worker(name: str) -> str:
    time.sleep(1.0)  # ❌ 不让出控制权
    return f"{name} 完成"
```

**用 `gather` 跑 3 个，耗时 3.00s（完全串行），而且不报任何错。**

**解药**：`await asyncio.sleep()`，或者用 `asyncio.to_thread()` 包装同步函数。

### 坑 2：`AsyncClient` 初始化是同步阻塞

```python
async def achat(...):
    async with httpx.AsyncClient(...) as client:   # ❌ 每次约 150ms 阻塞
        ...
```

**解药**：创建一次，全程复用。

```python
async with httpx.AsyncClient(...) as shared:
    results = await asyncio.gather(*(achat(..., client=shared) for _ in range(6)))
```

**通用原则**：异步程序里，**「初始化昂贵」的对象要建一次复用**（客户端、连接池、模型）。

### 坑 3：定义了函数但没接线（今天踩了三次）

| 次数 | 改了什么 | 漏了什么 |
|---|---|---|
| 1 | `achat` 加了 `client` 参数 | 调用方没传 → 数据其实是旧行为 |
| 2 | 定义了 `run_one` | `run_serial` 没调它 → 故障注入完全没生效 |
| 3 | 定义了 `achat_with_retry` | `arun_agent` 还是调 `achat` → 重试没发生 |

**这个模式的危险**：不报错、产出假数据、**静态检查抓不到**（pyright 和 ruff 都不报「函数定义了没被调用」）。

**防线**：`scratch/check_dead_code.py`——用 AST 找出「只出现在定义处」的函数。

### 坑 4：服务端错误的假设

猜「模型名不存在」会返回 404，**实测是 400**。

**重试逻辑里的可重试状态码必须按服务商文档或实测确定**，不能凭直觉——猜错会导致「该重试的放弃了」或「不该重试的反复烧钱」。

### 坑 5：网络故障没有隔离

第一次跑批量时，一个 `RemoteProtocolError` 让整个程序崩掉，**已经跑完的任务结果全丢**。

**解药**：在 Agent 层兜住 `httpx.HTTPError`，把它转换成「带 error 字段的返回值」，而不是向上抛。

## 九、决策速查

### 写异步代码时的判断顺序

```
这个操作是 IO 还是 CPU？
├─ IO
│   ├─ 有异步库？ → await（httpx.AsyncClient）
│   └─ 只有同步库？ → asyncio.to_thread（少量调用可以，大规模要换库）
└─ CPU
    └─ 耗时多少？
        ├─ 微秒级 → 忽略
        └─ 毫秒级以上 → run_in_executor(ProcessPoolExecutor)
```

### 并发控制的三个参数

| 参数 | 作用 | 本项目的值 |
|---|---|---|
| `Semaphore(n)` | 限制同时执行的任务数 | 命令行可配，默认 3 |
| `asyncio.wait_for` | 单个请求的总时限 | `settings.request_timeout` |
| `max_attempts` | 重试次数（指数退避） | 3 次（0.5s → 1s → 2s） |

### 失败处理的三个层次

| 层次 | 做法 |
|---|---|
| **重试** | 只重试可恢复的错误（网络、429、5xx），4xx 立刻放弃 |
| **隔离** | 每个任务兜住异常，返回结构化结果而不是上抛 |
| **报告** | 统计成功/失败数量，失败原因可见 |

## 十、一句话总结

> **异步把「等待」重叠起来，但它只省时间、不省工作量；**
> **它只对 IO 有效，CPU 密集要用进程池；**
> **它的代价是「一阻塞全阻塞」，所以任何同步调用都必须被 `to_thread` 或进程池隔离。**
