## 五、面试能用上的三个故事

### 故事 1：我怎么优化上下文成本

四个版本的对照实验：

- 不压缩：2175 tokens / ¥0.00438，5/5 信息覆盖
- 头尾截断 800 字符：1032 tokens（**降 53%**）/ ¥0.00283（降 35%），但**只找到 3/5 类问题**
- 按日志级别筛选 40 行：1866 tokens / ¥0.00390，5/5
- **按日志级别筛选 20 行：1253 tokens（降 42%）/ ¥0.00317（降 28%），5/5，且答案质量更高**

> 两个降幅不一样：压缩只作用于输入，输出 token 不变，所以成本降幅总小于 token 降幅。

**结论**：删对东西比删得多重要。去掉噪声行后信号占比提升，模型的分类和因果分析反而更好。

### 故事 2：ReAct 和 Function Calling 怎么选

两种范式都手写实现过，实测：

| 问题 | Function Calling | ReAct |
|---|---|---|
| 幂运算 | 1440 tok / 1.48s | 634 tok / 1.39s |
| 日志总结 | 2064 tok / 2.66s | 1254 tok / 2.86s |
| 双工具 | 1487 tok / **1.45s** | 1068 tok / **2.64s** |

**关键发现**：ReAct 输入 token 低 28-56%（工具说明是自然语言，比 JSON Schema 短 4.56 倍），但需要并行工具调用时 Function Calling 快 82%——**因为 ReAct 的文本格式一次只能输出一组 Action。**

### 故事 3：异步踩过的坑

三个各 1 秒的同步任务，用 `asyncio.gather` 跑还是 **3.00 秒**——**并发静默失效，不报错、结果正确**。归因到 `time.sleep` 不让出控制权，解药是 `to_thread` 包装（改完 1.00s）。

而且不止 `time.sleep`：同步 HTTP 库、文件 IO、CPU 密集循环都有同样问题。**唯一的发现方式是测耗时。**
